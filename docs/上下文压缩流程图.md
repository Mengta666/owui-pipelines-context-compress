# 上下文压缩模块完整详尽流程图

---

## 1. 模块边界

严格按代码职责划分，上下文压缩相关能力由下面几部分共同组成：

- `ContextManager.prepare_turn()`
- `HistoryCompactor.apply_lightcompact()`
- `HistoryCompactor.compact_if_needed()`
- `HistoryCompactor._compact_history()`
- `HistoryCompactor._merge_summary()`
- `HistoryCompactor._enforce_hard_limit()`
- `Runtime._fit_request_messages_to_budget()`
- `Runtime._budget_tool_result_message()`
- `WorkspaceStore.write_transcript()`
- `WorkspaceStore.write_text_artifact()`

也就是说，它不是“只有 full compaction 才算压缩”，而是一个**分层压缩系统**：

1. 轻压缩历史大消息  
2. 摘要压缩中段历史  
3. 工具结果超长外置  
4. 请求发送前再次按预算裁剪

### 4.1 Lightcompact replacement 结构

压缩后保留在 history 里的替代文本结构是：

```text
[lightly compacted older <label>; full original moved out of inline history]
Summary:
- ...
- ...

Original size: <chars> chars across <lines> lines
Full original saved as transcript artifact: <artifact_label>
Use read_transcript with that path if exact details are needed.
```

也就是说，lightcompact 的本质是：

- **原文外置**
- **history 内保留短摘要**
- **保留可恢复入口**

### 6.1 分组策略含义

`_group_history()` 的关键点是：

- `assistant_tool_use`
- 后续连续的 `user_tool_result`

会被合并为一个逻辑组。

这样 full compaction 时压缩的是“一个工具行动单元”，而不是把 tool_call 和 tool_result 拆散。

### 6.2 切分策略含义

`_split_groups()` 不是简单按位置切历史，而是构造三类保留区：

- **early groups**：开头锚点  
- **recent groups**：结尾工作集  
- **pinned user groups**：最近用户显式约束

真正允许被压缩成 transcript + summary 的，是中间的 `middle_groups`。

### 9.1 Hard Limit 的作用

这不是正常压缩路径，而是**最后保险丝**。  
如果 full compaction 后仍然超窗口，就不再尝试摘要，而是：

- 保一个 `memory_summary`
- 保极少量尾部工作集
- 保近期用户消息
- 其余丢弃

## 10. 请求发送前的最后一层预算裁剪

`HistoryCompactor` 处理的是 **history 级别压缩**。  
但真正发给模型前，`Runtime._fit_request_messages_to_budget()` 还会对**单次请求消息集**再做一次预算控制。

```mermaid
flowchart TD
    Start([开始 _fit_request_messages_to_budget]) --> Sanitize[清洗消息以符合模型要求]
    Sanitize --> CalcBudget[计算可用 Token 预算 budget]
    
    CalcBudget --> Check{总额 <= budget?}
    Check -- 是 --> ReturnOriginal([直接返回])

    subgraph Phase1 [第一阶段：消息逐条删除]
        Check -- 否 --> WhileLoop{"while 长度 > 预留数 + 1 <br/>且 依然超支?"}
        WhileLoop -- 是 --> DeleteMiddle["删除中间消息<br/>(索引为 preserve_prefix_count)"]
        DeleteMiddle --> WhileLoop
    end

    WhileLoop -- 否 --> FinalCheck{依然超支?}
    FinalCheck -- 否 --> ReturnTrimmed([返回删除后的列表])

    subgraph Phase2 [第二阶段：消息内容暴力截断]
        FinalCheck -- 是 --> Selection[确定截断目标: <br/>1. 最后一条消息 <br/>2. 逆序 prefix 消息]
        Selection --> TrimCall["调用 _trim_message_to_budget"]
        
        subgraph DeepTrim [Deep Trim 逻辑]
            TrimCall --> HeadTail["尝试保留两端 (Head/Tail Trim)"]
            HeadTail --> SizeCheck{达标?}
            SizeCheck -- 否 --> Shrink[继续缩短 Head/Tail 长度]
            Shrink --> HeadTail
            SizeCheck -- 是 --> Replace[替换原消息内容]
        end
        
        Replace --> Degrade["保底策略: <br/>trim_text(original, 160, 60)"]
    end

    Degrade --> BudgetCheck{整体 Token <= Budget?}
    BudgetCheck -- 否 --> Selection
    BudgetCheck -- 是 --> ReturnFinal([返回最终精简结果])

    %% 样式
    style ReturnOriginal fill:#9f9
    style ReturnFinal fill:#9f9
    style Selection fill:#fff4dd
    style Degrade fill:#ffb3ba
```

### 10.1 这层与 full compaction 的区别

- `full compaction`：改变 session history 的长期结构  
- `request budget fit`：只保证**这一次请求**能塞进窗口

它不会写 transcript，也不会写 summary，只是即时裁剪。

## 11. 超长工具结果的并行压缩路径

上下文压缩不仅发生在 `prepare_turn` 之前。  
运行中如果工具返回的内容过大，还会进入一条单独的“工具结果预算化”路径。

```mermaid
flowchart TD
    Start([开始 _budget_tool_result_message]) --> Flatten[展平 tool_result.content]
    Flatten --> SetBudget[设定阈值: TOOL_RESULT_INLINE_BUDGET_CHARS]

    SetBudget --> BudgetCheck{内容长度 <= 阈值?}

    %% 路径 1: 短内容
    BudgetCheck -- "是 (小结果)" --> KeepOriginal[normalize_history_item<br/>原样保留内容]
    KeepOriginal --> ReturnItem([返回历史项])

    %% 路径 2: 长内容处理
    BudgetCheck -- "否 (超长内容)" --> Offload[写入 Artifact 存储]
    
    subgraph Compression [智能摘要与替换]
        Offload --> HeadExtract["_tool_result_progress_head<br/>(从前 24 行提取 Meta 信息)"]
        HeadExtract --> Render["render_lightcompact_replacement<br/>(构建轻量化描述)"]
        
        Render --> Assemble["组装替代消息: <br/>1. 溢出警告 <br/>2. 关键元数据头部 <br/>3. Artifact 引用标签"]
    end

    Assemble --> CreateRef[创建 internal_artifact_ref]
    CreateRef --> ReturnOffloaded([返回替代消息 + 引用引用项])

    %% 样式美化
    style BudgetCheck fill:#fff4dd,stroke:#d4a017
    style KeepOriginal fill:#c8e6c9,stroke:#2e7d32
    style Offload fill:#f8bbd0,stroke:#880e4f
    style Compression fill:#f3e5f5,stroke:#7b1fa2,stroke-dasharray: 5 5
```

### 11.1 为什么这条路径重要

它解决的问题是：

- 工具本轮读取的内容可能非常大
- 这部分内容还没来得及进入下一轮压缩
- 如果直接把完整 tool result 放进 history，会把下一轮 prompt 顶爆

因此 runtime 会先做一次**工具结果级别的内联预算控制**。

---

## 12. 工作区持久化与恢复点

压缩模块依赖 `WorkspaceStore` 提供两个关键持久化点：

### 12.1 Transcript

- 由 `write_transcript(chat_id, delta_messages)` 写入
- 用于 full compaction 后恢复被移出的中段历史

### 12.2 Artifact

- 由 `write_text_artifact(chat_id, prefix, text)` 写入
- 用于 lightcompact 和 oversized tool result 的原文保存

它们在下一轮不会自动回灌到 prompt，而是通过：

- `read_transcript`
- `read_prompt_history`

等工具按需恢复。

## 13. 全链路关系图（最完整版本）

```mermaid
flowchart TD
    %% 阶段一：感知与预处理
    subgraph Detection [感知与轻量化阶段]
        A[Session history 增长] --> B(prepare_turn)
        B --> D[apply_lightcompact]
        D --> E{超过 Light 阈值?}
        E -- 是 --> G[筛选长文本/工具结果]
        G --> I[原文外置为 Artifact]
        I --> K[历史原消息替换为轻摘要]
        K --> L[更新 Snapshot]
        E -- 否 --> F[保留现状]
    end

    %% 阶段二：深度压缩与总结
    subgraph Compaction [深度压缩阶段]
        F & L --> M{达到 Compact 阈值?}
        M -- 是 --> P[compact_if_needed]
        P --> Q{熔断检查?}
        Q -- 否 --> R[_compact_history]
        R --> T[消息分组/切分/增量计算]
        T --> ZA[LLM 总结机制: Strict/Loose/Fallback]
        ZA --> AB[历史重建: Summary + Early + Recent]
        M -- 否 --> O
    end

    %% 阶段三：请求前的硬裁剪
    subgraph Budgeting [硬预算阶段]
        O(prepare_turn 结束) --> AE[build_messages]
        AE --> AF[fit_request_messages_to_budget]
        AF --> AG{仍超预算?}
        AG -- 是 --> AI[逐层裁剪: 删中间 -> 截长单条]
        AI --> AH[发模型请求]
        AG -- 否 --> AH
    end

    %% 阶段四：后置处理
    subgraph PostProcess [结果处理阶段]
        AH --> AL{结果过大?}
        AL -- 是 --> AN[结果外置为 Artifact + 插入 Ref]
        AN --> AM[写入 History]
        AL -- 否 --> AM
        AM --> AR([下一轮循环])
    end

    %% 全局连接
    AB --> AD[保存状态]
    AD --> O
    Q -- 是 --> O
```
